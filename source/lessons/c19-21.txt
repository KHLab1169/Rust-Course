=== 19.1
@idea
**Patterns** describe the shape of a value, and they appear in many more places than `match`. A `let` statement is a pattern: `let (x, y) = point;` destructures a tuple. Function parameters are patterns: `fn print(&(x, y): &(i32, i32))`. So are the targets of `for` loops (`for (i, item) in list.iter().enumerate()`), `if let`, `while let`, let-else, and closure parameters. Learning patterns once pays off everywhere.

Patterns come in two kinds. An **irrefutable** pattern matches any possible value of its type: `x`, `(a, b)` for a pair, `Point { x, y }`. A **refutable** pattern can fail to match: `Some(x)` does not match `None`, and `1..=5` does not match 9. Where a pattern appears decides which kind is allowed. `let`, function parameters and `for` loops require irrefutable patterns, because there is no sensible thing to do if they fail. `if let`, `while let`, let-else and `match` arms accept refutable ones, because they say what happens on failure.

The compiler enforces this: `let Some(x) = maybe;` alone is an error (use `if let` or let-else), and `if let x = 5` is a warning, because the condition is always true. Match arms are refutable patterns, except that the last arm often uses an irrefutable catch-all to make the match exhaustive.
@how
- Patterns appear in `let`, parameters, `for`, `if let`, `while let`, let-else, `match`, closures.
- Irrefutable: always match (`x`, `(a, b)`, struct destructuring).
- Refutable: may fail (`Some(x)`, literals, ranges).
- `let`/parameters/`for` need irrefutable; `if let`/`while let`/let-else/`match` handle refutable.
- Use let-else to bind a refutable pattern for the rest of a scope.
@example rust: Patterns everywhere
struct Point {
    x: i32,
    y: i32,
}

fn print_coords(&(x, y): &(i32, i32)) -> String {              // pattern in a parameter
    format!("({x}, {y})")
}

fn main() {
    let (a, b, c) = (1, "two", 3.0);                              // let destructures a tuple
    let Point { x, y: height } = Point { x: 5, y: 12 };           // and a struct
    println!("{a} {b} {c} | x={x} height={height}");
    println!("{}", print_coords(&(3, -4)));

    for (i, word) in ["alpha", "beta"].iter().enumerate() {       // for-loop pattern
        println!("{i}: {word}");
    }

    let mut stack = vec![(1, 'a'), (2, 'b')];
    while let Some((n, ch)) = stack.pop() {                        // refutable, in while let
        println!("popped {n}{ch}");
    }

    let pairs = [(1, 2), (3, 4)];
    let sums: Vec<i32> = pairs.iter().map(|&(l, r)| l + r).collect();   // closure parameter
    println!("{sums:?}");

    let config = Some("8080");
    let Some(port) = config else { return };                       // refutable with let-else
    println!("port {port}");
}
@note
The same pattern syntax destructured a tuple and a struct in `let`, unpacked a reference to a tuple in a function parameter, split `enumerate`'s pairs in a `for` loop, drove a `while let` loop, and unpacked tuples in a closure. let-else accepted a refutable pattern because it says what to do when it fails.
@example rust fail: let needs an irrefutable pattern
fn main() {
    let maybe_name: Option<&str> = None;
    let Some(name) = maybe_name;
    println!("{name}");
}
@note
`Some(name)` does not cover `None`, so a plain `let` cannot use it: the compiler says the pattern is refutable and suggests `if let` or `let ... else`. Requiring irrefutable patterns in `let` is what guarantees that every variable is initialised.
@mistakes
- **`let Some(x) = opt;`.** Use `if let`, let-else or `match`.
- **Forgetting that parameters and `for` loops take patterns.** Destructuring there removes boilerplate.
- **`if let` with an irrefutable pattern.** The condition is always true; just use `let`.
@keys
- Patterns appear in let, parameters, for, if let, while let, let-else, match and closures.
- Irrefutable patterns always match; refutable ones may fail.
- Contexts without a failure branch require irrefutable patterns.
- let-else binds a refutable pattern with an explicit failure path.

=== 19.2
@idea
Pattern syntax is a small language of its own. **Literals** match exact values; **named variables** match anything and bind it (careful: a name in a `match` arm creates a new variable, **shadowing** any outer one with the same name; compare with an outer value using a guard instead). **`|`** combines alternatives (`1 | 2`), and **ranges** match spans of numbers or chars (`'a'..='j'`, `90..=100`).

**Destructuring** takes apart structs (`Point { x, y: 0 }` matches points on the x axis and binds `x`), enums including nested ones (`Message::ChangeColor(Color::Rgb(r, g, b))`), tuples and references. **Ignoring** parts: `_` ignores one value without binding it, `_name` binds but silences the unused warning, and `..` ignores the remaining fields or elements (`Point { x, .. }`, `(first, .., last)`).

Two extras complete the toolbox. A **match guard**, `if condition` after a pattern, adds a check the pattern alone cannot express (`Some(n) if n % 2 == 0`). An **`@` binding** tests a value against a pattern *and* binds it: `id @ 3..=7` matches the range and keeps the number in `id`. Combined, these let one `match` express rules that would otherwise take nested `if` statements.
@how
- Literals, variables (new bindings!), `|` alternatives, `a..=b` ranges.
- Destructure structs `S { a, b: 0 }`, enums, nested enums, tuples, references.
- Ignore: `_` (no binding), `_x` (binding, no warning), `..` (the rest).
- Guards: `pattern if cond =>`; compare to outer variables with guards.
- `name @ pattern` binds while testing.
@example rust: The whole pattern toolbox
enum Color {
    Rgb(u8, u8, u8),
    Hsv(u16, u8, u8),
}

enum Message {
    Move { x: i32, y: i32 },
    Write(String),
    ChangeColor(Color),
    Quit,
}

struct Point3 {
    x: i32,
    y: i32,
    z: i32,
}

fn classify(n: i32, lucky: i32) -> String {
    match n {
        0 => "zero".into(),
        1 | 2 | 3 => "small".into(),
        x if x == lucky => format!("{x} is the lucky number"),     // guard compares with an outer value
        id @ 4..=9 => format!("single digit {id}"),
        n if n < 0 => "negative".into(),
        _ => "big".into(),
    }
}

fn describe(msg: &Message) -> String {
    match msg {
        Message::Move { x: 0, y } => format!("vertical move by {y}"),
        Message::Move { x, y: 0 } => format!("horizontal move by {x}"),
        Message::Move { x, y } => format!("diagonal to ({x}, {y})"),
        Message::Write(text) if text.is_empty() => "empty note".into(),
        Message::Write(text) => format!("note: {text}"),
        Message::ChangeColor(Color::Rgb(r, _, b)) => format!("rgb, red {r} blue {b}"),
        Message::ChangeColor(Color::Hsv(h, ..)) => format!("hsv, hue {h}"),
        Message::Quit => "quit".into(),
    }
}

fn main() {
    println!("{:?}", [0, 2, 13, 7, -5, 42].map(|n| classify(n, 13)));
    let inbox = [
        Message::Move { x: 0, y: 5 }, Message::Move { x: -3, y: 0 }, Message::Move { x: 1, y: 1 },
        Message::Write(String::new()), Message::Write("hi".into()),
        Message::ChangeColor(Color::Rgb(255, 0, 64)), Message::ChangeColor(Color::Hsv(210, 50, 80)), Message::Quit,
    ];
    for m in &inbox {
        println!("{}", describe(m));
    }
    let p = Point3 { x: 1, y: 2, z: 3 };
    let Point3 { x, .. } = p;
    let (first, .., last) = (10, 20, 30, 40);
    println!("x = {x}, z unused = {}, first {first}, last {last}", p.z + p.y - p.y);
}
@note
`classify` uses literals, alternatives, a guard that compares with the outer `lucky` value, an `@` binding on a range, and a catch-all. `describe` destructures struct variants with literal fields to tell vertical, horizontal and diagonal moves apart, adds a guard on `Write`, and reaches into a nested enum while ignoring parts with `_` and `..`.
@example rust: A named variable in a pattern shadows, it doesn't compare
fn main() {
    let expected = 5;
    let value = Some(10);
    match value {
        Some(expected) => println!("matched, and `expected` is now {expected} (a new variable!)"),
        None => println!("none"),
    }
    match value {
        Some(n) if n == expected => println!("equal to {expected}"),
        Some(n) => println!("{n} is not {expected}: the guard compared properly"),
        None => println!("none"),
    }
}
@note
In the first `match`, `Some(expected)` did not compare with the outer `expected`; it created a new variable that matched anything and shadowed the outer one, which is a classic surprise. The second `match` uses a guard to compare against the outer value correctly.
@mistakes
- **Expecting a variable name in a pattern to compare.** It binds a new variable; use a guard.
- **`_x` when you mean `_`.** `_x` still binds (and can move a value); `_` does not.
- **Long if-else chains on enum fields.** A match with destructuring and guards is clearer.
@keys
- Literals, `|`, ranges and named bindings form the basics.
- Destructure structs, enums, tuples and references; ignore with `_` and `..`.
- Guards add conditions; `@` binds while testing.
- Names in patterns bind new variables, they do not compare.

=== 19.3
@idea
**Slice patterns** match on the **shape** of a slice or array. `[]` matches an empty slice, `[x]` exactly one element, `[first, second]` exactly two, and `..` stands for "any number of elements here": `[first, ..]`, `[.., last]` or `[first, .., last]`. Combine `..` with an `@` binding to capture the middle or the rest: `[head, tail @ ..]` binds the first element and a sub-slice of the remainder, a natural fit for recursive processing and for parsing command words like `["move", x, y]`.

**Let chains** (stable in the 2024 edition) combine several `let` patterns and boolean conditions in a single `if` or `while`, joined with `&&`: `if let Some(user) = find(id) && user.active && let Some(email) = &user.email { ... }`. Each binding is available in the following conditions and in the body, replacing nested `if let` pyramids with one flat condition.

The **`matches!`** macro answers "does this value match this pattern?" as a `bool`, guards included: `matches!(c, 'a'..='z' | '_')` or `matches!(response, Ok(r) if r.status == 200)`. It is ideal for `filter` closures, assertions and simple checks where a full `match` would be noise.
@how
- `[]`, `[x]`, `[a, b]`, `[first, ..]`, `[.., last]`, `[first, .., last]`.
- `[head, tail @ ..]` binds the rest as a sub-slice.
- Let chains: `if let P = a && cond && let Q = b { ... }` (edition 2024).
- `matches!(value, pattern)` and `matches!(value, pattern if guard)` return bool.
- Slice patterns on `&str` lists make command parsing readable.
@example rust: Slices, let chains and matches!
fn describe(nums: &[i32]) -> String {
    match nums {
        [] => "empty".into(),
        [one] => format!("just {one}"),
        [first, second] => format!("a pair: {first} and {second}"),
        [first, .., last] if first == last => format!("{} items, same at both ends ({first})", nums.len()),
        [first, middle @ .., last] => format!("{first}..{last} with {} in the middle", middle.len()),
    }
}

fn sum(nums: &[i32]) -> i32 {
    match nums {
        [] => 0,
        [head, tail @ ..] => head + sum(tail),
    }
}

fn command(input: &str) -> String {
    let words: Vec<&str> = input.split_whitespace().collect();
    match words.as_slice() {
        ["go", direction] => format!("going {direction}"),
        ["take", item, "from", place] => format!("taking {item} from the {place}"),
        ["say", rest @ ..] if !rest.is_empty() => format!("saying {:?}", rest.join(" ")),
        _ => format!("unknown command {input:?}"),
    }
}

struct User {
    name: &'static str,
    active: bool,
    email: Option<&'static str>,
}

fn main() {
    for list in [&[][..], &[7], &[1, 2], &[4, 9, 4], &[1, 2, 3, 4, 5]] {
        println!("{}", describe(list));
    }
    println!("recursive sum: {}", sum(&[1, 2, 3, 4]));
    for c in ["go north", "take lamp from table", "say hello there", "dance"] {
        println!("{}", command(c));
    }

    let users = [User { name: "ada", active: true, email: Some("ada@example.com") },
                 User { name: "ben", active: false, email: Some("ben@example.com") },
                 User { name: "cy", active: true, email: None }];
    for u in &users {
        if u.active && let Some(email) = u.email && email.ends_with("@example.com") {
            println!("emailing {} at {email}", u.name);
        }
    }
    let identifier_chars = "snake_case_42".chars().filter(|c| matches!(c, 'a'..='z' | '0'..='9' | '_')).count();
    println!("{identifier_chars} valid identifier characters; is the first a letter? {}", matches!("snake".chars().next(), Some(c) if c.is_alphabetic()));
}
@note
The slice patterns read like a description of each shape, including a guard comparing the ends and `middle @ ..` capturing the rest. The recursive `sum` peels off the head each time. Command parsing matches word lists directly, and the let chain replaced two nested `if let`s: only Ada is active and has an email. `matches!` turned patterns into booleans.
@example rust fail: Slice patterns must cover every length
fn first_two(nums: &[i32]) -> (i32, i32) {
    match nums {
        [a, b, ..] => (*a, *b),
        [a] => (*a, 0),
    }
}

fn main() {
    println!("{:?}", first_two(&[1, 2, 3]));
}
@note
Exhaustiveness checking applies to slice shapes too: the empty slice `[]` is not covered, and the compiler names it as the missing pattern. Adding `[] => (0, 0)` completes the match.
@mistakes
- **Indexing with `nums[0]` after checking `len()`.** Slice patterns check and bind in one step.
- **Nested `if let` pyramids.** Use let chains (edition 2024).
- **A full `match` just to get a bool.** Use `matches!`.
@keys
- Slice patterns match shapes: `[]`, `[x]`, `[first, .., last]`, `[head, tail @ ..]`.
- They make recursive processing and word-list parsing readable.
- Let chains combine `let` patterns and conditions with `&&`.
- `matches!` returns whether a value fits a pattern.

=== 20.1
@idea
Rust's safety checks are conservative: some correct programs cannot be proven safe by the compiler. **`unsafe`** blocks let you do five extra things, the "unsafe superpowers": dereference a **raw pointer**, call an **unsafe function** (including foreign C functions), access or modify a **mutable static** variable, implement an **unsafe trait** (like `Send`), and access fields of a **union**. Everything else, including the borrow checker, stays in force inside `unsafe`.

`unsafe` does not mean "dangerous code" so much as "**the programmer**, not the compiler, **guarantees** these rules": no null or dangling pointer dereferences, no data races, no aliasing a `&mut`. Get it wrong and the program has **undefined behaviour**, which can corrupt memory silently. So keep unsafe blocks tiny, and document each with a `// SAFETY:` comment explaining why the rules hold.

The key technique is a **safe abstraction**: wrap the unsafe code in a function with a safe signature whose checks guarantee the unsafe part is sound. The standard library's `split_at_mut` is the classic example: borrowing two non-overlapping halves of a slice mutably at once is safe, but the borrow checker cannot see that they don't overlap, so it uses raw pointers internally, after asserting the split point is in bounds. Callers get a safe function; the unsafety is contained and reviewed in one place.
@how
- Raw pointers: `*const T`, `*mut T`; creating them is safe, dereferencing needs `unsafe`.
- `unsafe { ... }` blocks for the five superpowers only; borrow checking still applies.
- `unsafe fn` for functions with preconditions the caller must uphold.
- Write `// SAFETY:` comments explaining why each block is sound.
- Wrap unsafe code in safe functions with checks; prefer existing safe APIs.
@example rust: A safe split_at_mut built on raw pointers
use std::slice;

fn split_at_mut(values: &mut [i32], mid: usize) -> (&mut [i32], &mut [i32]) {
    let len = values.len();
    assert!(mid <= len, "mid {mid} out of bounds for length {len}");
    let ptr = values.as_mut_ptr();
    // SAFETY: mid <= len was checked, so both ranges are inside the slice,
    // and they do not overlap, so the two &mut never alias.
    unsafe { (slice::from_raw_parts_mut(ptr, mid), slice::from_raw_parts_mut(ptr.add(mid), len - mid)) }
}

static mut CALLS: u32 = 0;

fn count_call() -> u32 {
    // SAFETY: this program is single-threaded, so nothing else accesses CALLS concurrently.
    unsafe {
        CALLS += 1;
        CALLS
    }
}

fn main() {
    let mut data = [1, 2, 3, 4, 5, 6];
    let (left, right) = split_at_mut(&mut data, 2);
    left[0] *= 100;
    right[0] *= 10;
    println!("{data:?}");

    let x = 42;
    let p = &x as *const i32;                 // creating a raw pointer is safe
    // SAFETY: p points to x, which is alive and valid for reads.
    println!("through a raw pointer: {}", unsafe { *p });
    count_call();
    println!("calls: {}", count_call());
}
@note
`split_at_mut` has a safe signature: it checks the bounds, then uses raw pointers to create two mutable slices the borrow checker could not prove disjoint. Callers modify both halves with no `unsafe` in sight. Dereferencing a raw pointer and touching a mutable static both required `unsafe`, each with a SAFETY comment stating why it is sound.
@example rust fail: The borrow checker can't see that the halves don't overlap
fn split_at_mut(values: &mut [i32], mid: usize) -> (&mut [i32], &mut [i32]) {
    let len = values.len();
    assert!(mid <= len);
    (&mut values[..mid], &mut values[mid..])
}

fn main() {}
@note
Without unsafe code, the compiler sees two mutable borrows of `values` at the same time and refuses, even though the ranges never overlap. This is exactly the situation unsafe exists for: a correct program the checker cannot prove, wrapped in a small, carefully justified block.
@mistakes
- **Large unsafe blocks.** Keep them minimal so the risky part is easy to review.
- **Unsafe without a SAFETY comment.** The next reader cannot check your reasoning.
- **Reaching for unsafe to fix borrow errors.** Usually a safe restructuring exists (or a std function like `split_at_mut`).
@keys
- `unsafe` unlocks five superpowers; the borrow checker still applies.
- The programmer guarantees soundness; mistakes are undefined behaviour.
- Wrap unsafe code in small, checked, safe abstractions.
- Document every unsafe block with a SAFETY comment.

=== 20.2
@idea
Traits have a few advanced features worth knowing. **Associated types** (`type Item;` inside a trait) name a type the implementor chooses once: `Iterator` has one `Item` per iterator. A **generic parameter** (`trait From<T>`) instead allows many implementations for one type (`From<u8>`, `From<u16>`...). Use an associated type when there is exactly one sensible choice per implementor.

**Default type parameters** set a type parameter's default: `trait Add<Rhs = Self>`, which is why `impl Add for Point` means adding two Points. Implementing `std::ops` traits is **operator overloading**: `Add` for `+`, `Mul` for `*`, `Neg` for unary `-`, `Index` for `[]`, and so on. Override the default when the right-hand side differs: `impl Add<Meters> for Millimeters`.

When two traits give a type methods with the same name, use **fully qualified syntax** to choose: `<Dog as Animal>::name()`. A **supertrait** requires another trait: `trait OutlinePrint: Display` lets the trait's methods use `to_string()`. And the **newtype pattern**, a tuple struct wrapping one value (`struct Wrapper(Vec<String>)`), lets you implement foreign traits on foreign types (sidestepping the orphan rule), add type safety (`Meters` vs `Feet`), or hide an inner type's API, at zero run-time cost.
@how
- Associated type: one choice per implementor (`type Item`); generic param: many impls.
- `impl Add for T` (default `Rhs = Self`); `impl Add<Other> for T` otherwise.
- Operator traits in `std::ops`: Add, Sub, Mul, Neg, Index, AddAssign...
- Disambiguate with `<Type as Trait>::method(...)`.
- Supertraits: `trait A: B`; newtypes: `struct Wrapper(Inner);`.
@example rust: Operators, supertraits and a newtype
use std::fmt;
use std::ops::{Add, Mul};

#[derive(Debug, Clone, Copy, PartialEq)]
struct Point {
    x: i32,
    y: i32,
}

impl Add for Point {                                   // Rhs defaults to Self
    type Output = Point;
    fn add(self, other: Point) -> Point {
        Point { x: self.x + other.x, y: self.y + other.y }
    }
}

impl Mul<i32> for Point {                              // a different right-hand side
    type Output = Point;
    fn mul(self, k: i32) -> Point {
        Point { x: self.x * k, y: self.y * k }
    }
}

impl fmt::Display for Point {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "({}, {})", self.x, self.y)
    }
}

trait OutlinePrint: fmt::Display {                     // supertrait: requires Display
    fn outline(&self) -> String {
        let s = self.to_string();
        let bar = "*".repeat(s.len() + 4);
        format!("{bar}\n* {s} *\n{bar}")
    }
}

impl OutlinePrint for Point {}

struct Csv(Vec<String>);                                // newtype: Display for a Vec, legally

impl fmt::Display for Csv {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "{}", self.0.join(","))
    }
}

#[derive(Debug, Clone, Copy)]
struct Meters(f64);
#[derive(Debug, Clone, Copy)]
struct Millimeters(f64);

impl Add<Meters> for Millimeters {
    type Output = Millimeters;
    fn add(self, m: Meters) -> Millimeters {
        Millimeters(self.0 + m.0 * 1000.0)
    }
}

fn main() {
    let p = Point { x: 1, y: 2 } + Point { x: 3, y: 4 };
    println!("{p} and doubled {}", p * 2);
    println!("{}", p.outline());
    println!("{}", Csv(vec!["tea".into(), "cake".into(), "scone".into()]));
    println!("{:?}", Millimeters(250.0) + Meters(1.5));
}
@note
`impl Add for Point` used the default right-hand side (another Point), while `Mul<i32>` and `Add<Meters>` chose different ones. `OutlinePrint` could call `to_string()` because its supertrait guarantees Display. The `Csv` newtype implemented Display for what is really a `Vec<String>`, which the orphan rule would otherwise forbid.
@example rust: Fully qualified syntax for same-named methods
trait Pilot {
    fn fly(&self) -> String;
}

trait Wizard {
    fn fly(&self) -> String;
}

struct Human;

impl Pilot for Human {
    fn fly(&self) -> String { "This is your captain speaking.".into() }
}

impl Wizard for Human {
    fn fly(&self) -> String { "Up!".into() }
}

impl Human {
    fn fly(&self) -> String { "*waving arms furiously*".into() }
}

trait Animal {
    fn baby_name() -> String;
}

struct Dog;

impl Dog {
    fn baby_name() -> String { "Spot".into() }
}

impl Animal for Dog {
    fn baby_name() -> String { "puppy".into() }
}

fn main() {
    let person = Human;
    println!("{}", person.fly());
    println!("{}", Pilot::fly(&person));
    println!("{}", Wizard::fly(&person));
    println!("{} / {}", Dog::baby_name(), <Dog as Animal>::baby_name());
}
@note
Calling `person.fly()` picks the method defined directly on the type; `Pilot::fly(&person)` and `Wizard::fly(&person)` choose the trait versions. For associated functions without `self`, there is nothing to infer the type from, so `<Dog as Animal>::baby_name()` names both the type and the trait.
@mistakes
- **Generic parameters where an associated type fits.** Callers then must annotate types everywhere.
- **Operator overloads with surprising meanings.** `+` should mean something like addition.
- **Fighting the orphan rule.** A newtype is the standard, zero-cost answer.
@keys
- Associated types: one per implementor; generic parameters: many implementations.
- `std::ops` traits overload operators; default type parameters keep the common case short.
- Fully qualified syntax picks between same-named methods.
- Supertraits require other traits; newtypes add safety and bypass the orphan rule.

=== 20.3
@idea
A few more type-system tools round out the language. A **type alias** (`type Kilometers = i32;` or `type Result<T> = std::result::Result<T, MyError>;`) gives an existing type a shorter or clearer name; unlike a newtype, it is the *same* type, with no extra safety. Aliases shine for long types such as `Box<dyn Fn() + Send + 'static>`.

The **never type**, `!`, is the type of expressions that never produce a value: `panic!`, `loop` without `break`, `continue`, `return`, `process::exit`. Because `!` can stand in for any type, a `match` arm can be `Err(_) => continue` while the others produce numbers. **Dynamically sized types** (DSTs) like `str`, `[T]` and `dyn Trait` have no size known at compile time, so they always sit behind a pointer (`&str`, `Box<[T]>`, `&dyn Trait`). Generic parameters have an implicit `Sized` bound; `T: ?Sized` relaxes it to accept DSTs behind references.

Functions are values too. A **function pointer** type `fn(i32) -> i32` refers to a named function and can be passed around; closures that capture nothing coerce to it, and fn pointers implement all three `Fn` traits. To **return closures**, use `impl Fn(...)` (one concrete closure type) or `Box<dyn Fn(...)>` (when different branches return different closures).
@how
- `type Name = LongType;` for readability; same type, no safety (unlike newtypes).
- `!` for diverging expressions; it coerces to any type.
- DSTs (`str`, `[T]`, `dyn Trait`) live behind pointers; `T: ?Sized` accepts them.
- `fn(A) -> B` function pointers; pass named functions or non-capturing closures.
- Return closures with `impl Fn` or `Box<dyn Fn>`.
@example rust: Aliases, never, fn pointers and returned closures

=== 20.4
@idea
**Macros** are code that writes code at compile time. You have used them since `println!`: they take a variable number of arguments, can introduce new syntax, and expand into ordinary Rust before type checking. Functions can't do either: a function has a fixed signature and runs at run time. The cost is that macros are harder to write, read and debug, so reach for them only when a function or generic will not do.

**Declarative macros** (`macro_rules!`) work by pattern matching on code. Each rule has a matcher and a transcriber: `($x:expr) => { ... }`. **Fragment specifiers** say what each piece may be: `expr` (an expression), `ident` (a name), `ty` (a type), `tt` (any single token tree), `literal`, `block`, `pat`. **Repetition** `$( ... ),*` matches zero or more comma-separated items (`+` for one or more), and the transcriber repeats code for each. Macros are **hygienic**: variables they introduce cannot clash with the caller's.

**Procedural macros** are Rust functions that receive a token stream and return one, compiled in a separate crate. They come in three kinds: **custom derive** (`#[derive(Serialize)]`), **attribute-like** (`#[route(GET, "/")]`) and **function-like** (`sql!(SELECT ...)`). Most programmers use them far more than they write them; Track 2's macro module covers writing one.
@how
- `macro_rules! name { (pattern) => { expansion }; ... }`.
- Fragments: `$e:expr`, `$i:ident`, `$t:ty`, `$x:tt`, `$l:literal`, `$b:block`, `$p:pat`.
- Repetition: `$( $x:expr ),*` in the matcher, `$( ... )*` in the transcriber; add `$(,)?` for a trailing comma.
- Hygiene keeps macro-internal names separate from the caller's.
- Procedural macros: derive, attribute and function-like, in a `proc-macro` crate.
@example rust: A vec-like macro, a hashmap literal and a generated function
use std::collections::BTreeMap;

macro_rules! my_vec {
    () => { Vec::new() };
    ( $( $x:expr ),+ $(,)? ) => {{
        let mut v = Vec::new();
        $( v.push($x); )+
        v
    }};
}

macro_rules! map {
    ( $( $k:expr => $v:expr ),* $(,)? ) => {{
        let mut m = BTreeMap::new();
        $( m.insert($k, $v); )*
        m
    }};
}

macro_rules! getter {
    ($name:ident, $field:ident, $t:ty) => {
        fn $name(&self) -> $t {
            self.$field.clone()
        }
    };
}

struct Config {
    host: String,
    port: u16,
}

impl Config {
    getter!(host, host, String);
    getter!(port, port, u16);
}

fn main() {
    let empty: Vec<i32> = my_vec![];
    let v = my_vec![1, 2 + 3, 4 * 4,];
    println!("{empty:?} {v:?}");
    let prices = map! { "tea" => 450, "cake" => 650, "scone" => 300 };
    println!("{prices:?}");
    let c = Config { host: "localhost".into(), port: 8080 };
    println!("{}:{}", c.host(), c.port());
}
@note
`my_vec!` has two rules: one for no arguments and one for a comma-separated list (with an optional trailing comma), whose `$( v.push($x); )+` repeats once per expression. `map!` uses the custom `=>` syntax a function could never accept, and `getter!` generates whole methods from an identifier and a type.
@example rust: Hygiene: a macro's variables don't leak
macro_rules! square_twice {
    ($x:expr) => {{
        let tmp = $x * $x;                // `tmp` belongs to the macro
        tmp * tmp
    }};
}

macro_rules! count {
    () => { 0usize };
    ($head:tt $($tail:tt)*) => { 1usize + count!($($tail)*) };
}

fn main() {
    let tmp = 3;
    let result = square_twice!(tmp + 1);
    println!("({tmp} + 1)^4 = {result}, and the caller's tmp is still {tmp}");
    println!("count!(a b c d) = {}", count!(a b c d));
}
@note
The macro's internal `tmp` did not clash with the caller's `tmp`, and the argument `tmp + 1` used the caller's variable: that is hygiene. The expression was also evaluated as a unit because `$x:expr` captures it whole. `count!` is a recursive macro that peels off one token tree per step.
@mistakes
- **Writing a macro when a function or generic would do.** Macros are harder to read and debug.
- **Forgetting repetition separators.** `$( $x:expr ),*` needs commas between items; add `$(,)?` to allow a trailing one.
- **Expecting macros to see types.** They work on tokens before type checking.
@keys
- Macros generate code at compile time and accept flexible syntax.
- `macro_rules!` matches patterns of fragments and repeats with `$(...)*`.
- Hygiene prevents name clashes between macro and caller.
- Procedural macros (derive, attribute, function-like) transform token streams.

=== 21.1
@idea
The final project builds a web server from scratch with only the standard library, which shows what frameworks do underneath. HTTP runs over **TCP**: a client opens a connection, sends a text **request**, and the server sends back a text **response**. `TcpListener::bind("127.0.0.1:7878")` claims a port, and `listener.incoming()` yields a `TcpStream` for each connection.

An HTTP request starts with a **request line**, `GET /index.html HTTP/1.1`, followed by headers and a blank line. Wrapping the stream in a `BufReader` and reading lines until the empty one gives you the request; often only the first line matters for routing. A response starts with a **status line**, `HTTP/1.1 200 OK`, then headers such as `Content-Length` (how many bytes of body follow), a blank line, and the body. Every line ends with `\r\n`.

The first version serves `hello.html` for `GET /` and a 404 page for everything else, choosing the status line and file with a `match` on the request line. It handles one connection at a time, and binding can fail (for example when the port is already in use, or a port below 1024 needs administrator rights), so real code handles that error instead of unwrapping.
@how
- `let listener = TcpListener::bind(addr)?;` `for stream in listener.incoming()`.
- Read the request line: `BufReader::new(&stream).lines().next()`.
- Response: status line, `Content-Length: N`, blank line, body; lines end with `\r\n`.
- Route with `match request_line.as_str() { "GET / HTTP/1.1" => ..., _ => 404 }`.
- Write with `stream.write_all(response.as_bytes())`.
@example rust: A server and a client in one program
use std::io::{BufRead, BufReader, Read, Write};
use std::net::{TcpListener, TcpStream};
use std::thread;

fn handle(mut stream: TcpStream) {
    let request_line = BufReader::new(&stream).lines().next().unwrap().unwrap();
    let (status, body) = match request_line.as_str() {
        "GET / HTTP/1.1" => ("HTTP/1.1 200 OK", "<h1>Hello!</h1><p>Hi from Rust</p>"),
        _ => ("HTTP/1.1 404 NOT FOUND", "<h1>Oops!</h1><p>Sorry, I don't know what you asked for.</p>"),
    };
    let response = format!("{status}\r\nContent-Length: {}\r\nContent-Type: text/html\r\n\r\n{body}", body.len());
    stream.write_all(response.as_bytes()).unwrap();
}

fn get(addr: std::net::SocketAddr, path: &str) -> String {
    let mut stream = TcpStream::connect(addr).unwrap();
    write!(stream, "GET {path} HTTP/1.1\r\nHost: localhost\r\n\r\n").unwrap();
    let mut response = String::new();
    stream.read_to_string(&mut response).unwrap();
    response
}

fn main() {
    let listener = TcpListener::bind("127.0.0.1:0").unwrap();        // port 0: any free port
    let addr = listener.local_addr().unwrap();
    let server = thread::spawn(move || {
        for stream in listener.incoming().take(2) {                    // serve two requests, then stop
            handle(stream.unwrap());
        }
    });
    for path in ["/", "/missing"] {
        let response = get(addr, path);
        let (head, body) = response.split_once("\r\n\r\n").unwrap();
        println!("GET {path:9} -> {} | body: {body}", head.lines().next().unwrap());
    }
    server.join().unwrap();
}
@note
The server read only the request line and matched on it to pick a status and body, then wrote a response with a correct `Content-Length`. A client in the same program sent two raw HTTP requests, so the whole exchange is visible: 200 for `/` and 404 for anything else. Binding to port 0 lets the operating system choose a free port.
@example rust: Binding can fail, so handle it

@mistakes
- **Forgetting `Content-Length` or the blank line.** Browsers wait or show garbage. Follow the format exactly, with `\r\n`.
- **Reading the whole request before responding.** Read up to the blank line; the body comes after.
- **Unwrapping `bind`.** Ports may be in use or need privileges; report the error.
@keys
- `TcpListener::bind` and `incoming()` accept TCP connections.
- An HTTP request starts with a request line; read it with a BufReader.
- A response is a status line, headers, a blank line and a body.
- Route by matching on the request line; handle bind errors.

=== 21.2
@idea
A single-threaded server handles one request at a time, so one slow request blocks everyone. Adding a `/sleep` route that waits five seconds shows it: while it sleeps, even `/` has to wait. Spawning a new thread per connection fixes that but has no limit: a flood of requests would create thousands of threads and exhaust the machine.

A **thread pool** keeps a fixed number of worker threads waiting for jobs. The Book designs the API first, the way you'd want to use it: `let pool = ThreadPool::new(4); pool.execute(|| handle(stream));`, mirroring `thread::spawn`. Then it builds the implementation to fit. `ThreadPool::new(size)` creates a **channel** and `size` **Workers**; each Worker owns a thread that loops, receiving jobs from the channel and running them. A job is a boxed closure: `type Job = Box<dyn FnOnce() + Send + 'static>;`. `execute` boxes the closure and sends it down the channel.

Since every worker receives from the same channel and the receiver can't be cloned, it is shared as **`Arc<Mutex<Receiver<Job>>>`**: a worker locks the mutex, takes the next job, and **releases the lock before running the job** (by letting the guard drop at the end of the `let` statement), so other workers can pick up jobs concurrently. This is the producer-consumer pattern from chapter 16, applied.
@how
- Design the API first: `ThreadPool::new(n)`, `pool.execute(closure)`.
- `type Job = Box<dyn FnOnce() + Send + 'static>;`
- Workers share `Arc<Mutex<mpsc::Receiver<Job>>>`.
- Worker loop: `let job = receiver.lock().unwrap().recv();` then run the job outside the lock.
- Validate `size > 0` in `new` (or return a Result from `build`).
@example rust: The ThreadPool, and why the lock must be released before running a job
use std::sync::{mpsc, Arc, Mutex};
use std::thread;
use std::time::{Duration, Instant};

type Job = Box<dyn FnOnce() + Send + 'static>;

pub struct ThreadPool {
    sender: mpsc::Sender<Job>,
    workers: Vec<thread::JoinHandle<()>>,
}

impl ThreadPool {
    pub fn new(size: usize) -> ThreadPool {
        assert!(size > 0, "a pool needs at least one thread");
        let (sender, receiver) = mpsc::channel::<Job>();
        let receiver = Arc::new(Mutex::new(receiver));
        let workers = (0..size)
            .map(|_| {
                let receiver = Arc::clone(&receiver);
                thread::spawn(move || loop {
                    let message = receiver.lock().unwrap().recv();   // guard dropped at the semicolon
                    match message {
                        Ok(job) => job(),                             // run without holding the lock
                        Err(_) => break,                              // channel closed: stop
                    }
                })
            })
            .collect();
        ThreadPool { sender, workers }
    }

    pub fn execute<F: FnOnce() + Send + 'static>(&self, f: F) {
        self.sender.send(Box::new(f)).unwrap();
    }

    pub fn finish(self) {
        drop(self.sender);                                            // close the channel
        for w in self.workers {
            w.join().unwrap();
        }
    }
}

fn main() {
    let pool = ThreadPool::new(4);
    let (done_tx, done_rx) = mpsc::channel();
    let start = Instant::now();
    for id in 0..8 {
        let done_tx = done_tx.clone();
        pool.execute(move || {
            thread::sleep(Duration::from_millis(100));                 // a "slow request"
            done_tx.send(id).unwrap();
        });
    }
    drop(done_tx);
    let mut finished: Vec<i32> = done_rx.iter().collect();
    finished.sort();
    let rounds = (start.elapsed().as_millis() as f64 / 100.0).round();
    println!("finished {finished:?} in about {rounds} rounds of 100 ms (4 workers, 8 jobs)");
    pool.finish();
}
@note
Eight 100 ms jobs on four workers finished in about two rounds, so four ran at once. That only works because each worker drops the lock before running its job: the `let` statement ends the guard's life, so the next worker can receive immediately. Holding the lock while running (for example `while let Ok(job) = receiver.lock().unwrap().recv()`) would serialise the pool.
@example rust: The mistake that serialises the pool
use std::sync::{mpsc, Arc, Mutex};
use std::thread;
use std::time::{Duration, Instant};

fn main() {
    let (tx, rx) = mpsc::channel::<Box<dyn FnOnce() + Send>>();
    let rx = Arc::new(Mutex::new(rx));
    let workers: Vec<_> = (0..4).map(|_| {
        let rx = Arc::clone(&rx);
        thread::spawn(move || {
            while let Ok(job) = rx.lock().unwrap().recv() {   // the guard lives for the whole loop body
                job();
            }
        })
    }).collect();
    let start = Instant::now();
    for _ in 0..4 {
        tx.send(Box::new(|| thread::sleep(Duration::from_millis(100)))).unwrap();
    }
    drop(tx);
    for w in workers {
        w.join().unwrap();
    }
    let rounds = (start.elapsed().as_millis() as f64 / 100.0).round();
    println!("4 jobs on 4 workers took about {rounds} rounds: one at a time");
}
@note
In a `while let`, the temporary lock guard lives until the end of the loop body, so each worker held the mutex while running its job, and the other workers waited. Four jobs on four workers took four rounds instead of one. The fix is to receive in a separate `let` statement, as in the previous example.
@mistakes
- **One thread per connection without a limit.** A burst of requests exhausts the machine. Use a pool.
- **Holding the mutex while running the job.** The pool becomes single-threaded. Receive in its own statement.
- **Designing the implementation before the API.** Write how you want to call it first.
@keys
- A thread pool runs jobs on a fixed set of workers.
- Jobs are `Box<dyn FnOnce() + Send + 'static>` sent through a channel.
- Workers share the receiver as `Arc<Mutex<Receiver<Job>>>`.
- Release the lock before running each job.

=== 21.3
@idea
A server should shut down **gracefully**: stop accepting new work, let in-flight requests finish, and then stop the worker threads cleanly, instead of having the process killed mid-request. In the thread pool, that logic belongs in **`impl Drop for ThreadPool`**, so it happens automatically whenever the pool goes out of scope.

Shutdown has two steps. First, **close the channel** by dropping the sender: each worker's `recv()` then returns `Err` once the queue is empty, which tells it to leave its loop. Second, **join every worker** so the program waits for them to finish their current job. Ownership makes both steps slightly tricky, because `drop` only receives `&mut self`, and you cannot move a field out of a borrowed struct. The Book's solution stores the sender as **`Option<Sender<Job>>`** and each worker's thread as `Option<JoinHandle<()>>` (or drains the vector), so `take()` can move them out, leaving `None` behind.

The demo server then stops after two requests with `listener.incoming().take(2)`, and the logs show the shutdown sequence: the pool is dropped at the end of `main`, the channel closes, each worker reports that it is disconnecting, and the joins complete. The same pattern (signal, drain, join) applies to any service with background workers.
@how
- `sender: Option<mpsc::Sender<Job>>`; `execute` uses `self.sender.as_ref().unwrap()`.
- In `Drop`: `drop(self.sender.take());` closes the channel.
- Then `for worker in self.workers.drain(..) { worker.thread.join().unwrap(); }`.
- Workers exit their loop when `recv()` returns `Err`.
- Demo: `incoming().take(2)` to stop after two requests.
@example rust: Drop for ThreadPool shuts everything down cleanly
use std::sync::{mpsc, Arc, Mutex};
use std::thread;

type Job = Box<dyn FnOnce() + Send + 'static>;

struct Worker {
    id: usize,
    thread: thread::JoinHandle<()>,
}

pub struct ThreadPool {
    workers: Vec<Worker>,
    sender: Option<mpsc::Sender<Job>>,
}

impl ThreadPool {
    pub fn new(size: usize) -> ThreadPool {
        let (sender, receiver) = mpsc::channel::<Job>();
        let receiver = Arc::new(Mutex::new(receiver));
        let workers = (0..size)
            .map(|id| {
                let receiver = Arc::clone(&receiver);
                let thread = thread::spawn(move || loop {
                    let message = receiver.lock().unwrap().recv();
                    match message {
                        Ok(job) => job(),
                        Err(_) => break,
                    }
                });
                Worker { id, thread }
            })
            .collect();
        ThreadPool { workers, sender: Some(sender) }
    }

    pub fn execute<F: FnOnce() + Send + 'static>(&self, f: F) {
        self.sender.as_ref().unwrap().send(Box::new(f)).unwrap();
    }
}

impl Drop for ThreadPool {
    fn drop(&mut self) {
        drop(self.sender.take());                      // 1. close the channel
        println!("channel closed; waiting for {} workers", self.workers.len());
        let mut ids = Vec::new();
        for worker in self.workers.drain(..) {         // 2. join every worker
            worker.thread.join().unwrap();
            ids.push(worker.id);
        }
        println!("joined workers {ids:?}");
    }
}

fn main() {
    let results = Arc::new(Mutex::new(Vec::new()));
    {
        let pool = ThreadPool::new(3);
        for request in ["/", "/sleep", "/about", "/"] {
            let results = Arc::clone(&results);
            pool.execute(move || {
                thread::sleep(std::time::Duration::from_millis(if request == "/sleep" { 80 } else { 10 }));
                results.lock().unwrap().push(request);
            });
        }
        println!("all jobs submitted; leaving the scope drops the pool");
    }
    let mut done = results.lock().unwrap().clone();
    done.sort();
    println!("every in-flight request finished before shutdown: {done:?}");
}
@note
When the pool went out of scope, `Drop` took the sender out of its `Option` and dropped it, so each worker's `recv` returned an error once the queue was empty and its loop ended; then every worker was joined. All four requests, including the slow `/sleep`, completed before the program moved on: a graceful shutdown.
@example rust fail: You can't move a field out of &mut self
use std::sync::mpsc;

    sender: mpsc::Sender<String>,
}

impl Drop for Pool {
    fn drop(&mut self) {
        drop(self.sender);
    }
}

    let (tx, _rx) = mpsc::channel();
    let _pool = Pool { sender: tx };
}
@note
`drop` gets `&mut self`, and moving `self.sender` out of a borrowed struct is not allowed: the compiler explains that the value is behind a mutable reference. Wrapping the field in an `Option` and calling `self.sender.take()` moves it out and leaves `None` in its place, which is exactly what the pool does.
@mistakes
- **Letting the process exit with workers mid-job.** Join them in `Drop`.
- **Joining before closing the channel.** Workers wait for jobs forever and the join never returns.
- **Moving fields out of `&mut self`.** Store them in `Option` and use `take()`.
@keys
- Graceful shutdown: stop accepting work, finish in-flight jobs, join workers.
- Put shutdown logic in `Drop` so it happens automatically.
- Close the channel first, then join.
- `Option` + `take()` moves owned fields out inside `drop`.
